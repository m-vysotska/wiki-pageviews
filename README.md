# wiki-pageviews — навичка для AI-агента

Навичка у форматі [Agent Skills](https://agentskills.io/specification), яка дозволяє агенту
відповідати на продуктові питання B2C-засновників («чи зростає інтерес до теми X?», «якою мовою
запускатися далі?») на основі статистики переглядів Wikipedia: знаходить потрібні статті в
усіх мовних розділах, рахує динаміку з інтервалами довіри, оцінює, наскільки результату можна
довіряти, малює графіки й збирає PDF-звіт на одну сторінку.

- `SKILL.md` — інструкція для агента (англійською, коротка, розрахована на Haiku-клас моделей).
- **Усі звіти українською**: PDF, графіки, `summary.md` і текст висновків агента (`notes.md`) —
  незалежно від мови запиту; `--ui en` лише на явне прохання. Команда `report` попереджає, якщо
  notes.md написано не українською. Російськомовна Вікіпедія (ru) навичкою не використовується.
- `scripts/wv.ts` — CLI на TypeScript, що виконує всю роботу з даними.
- `references/` — довідки, які агент читає лише за потреби.
- `evals/` — сценарії перевірки та журнал прогонів на Claude Haiku 4.5.

## Встановлення

```bash
cd wiki-pageviews
npm ci                           # pdfkit, svg-to-pdfkit, resvg (PNG), шрифт DejaVu; typescript — dev
node scripts/wv.ts doctor        # перевірка Node, залежностей і доступу до API
npm test && npm run typecheck    # 11 unit-тестів + tsc --strict
```

Потрібен **Node.js ≥ 22.18**: він виконує `.ts` напряму (type stripping), тож кроку збірки й
скомпільованих файлів немає. Залежності зафіксовані в `package-lock.json`. Аналіз працює навіть
без `npm ci` (залежності потрібні лише для PNG/PDF). Бажано задати `WV_CONTACT=<email>` —
Wikimedia вимагає контакт у User-Agent.

## Приклад

```bash
node scripts/wv.ts resolve --topic "Astronomy" --langs uk,pl,cs
node scripts/wv.ts analyze --topic "Astronomy" --langs uk,pl,cs --months 36 --ui uk
node scripts/wv.ts report  --analysis wv-output/astronomy-uk-pl-cs-2023-09-2026-08 --notes notes.md
```

Реальний результат (дані Wikimedia, вересень 2026): перегляди «Астрономії» в uk −59.6% за рік
(90% ДІ −64…−52%), але весь український розділ втратив 24.6% трафіку, тож відносно розділу −45.5%;
довіра medium (≈560 переглядів/міс). Щовересня пік — сезонність навчального року, вона
розпізнається й не вважається «сплеском».

## Як влаштовано

```
topic ──► Wikidata (search / sitelinks) ──► назва статті в кожній мові
                                            │  + перенаправлення (redirects)
                                            ▼
         Pageviews API: per-article (стаття + redirects), aggregate (весь розділ)
         └─ завжди повна історія 2015-07…останній повний місяць одним запитом → кеш
                                            ▼
analyze: YoY-зростання (12 vs ті самі 12 міс. рік тому) + paired bootstrap 90% ДІ
         частка від трафіку розділу (нормалізація) · місяці вгору/вниз · Sen's slope
         сплески (разові vs сезонні) · зростання без сплесків · попарні порівняння
         бал довіри high/medium/low з причинами · KEY FACTS (готові коректні речення)
                                            ▼
charts (SVG → PNG через resvg) · analysis.json · data.csv · summary.md
report: notes.md агента + графіки + таблиця + методика/обмеження → PDF (1 сторінка)
        CLAIM CHECK: кожен % у тексті звіряється з обчисленими числами
```

Файли: `lib/wiki.ts` (API), `lib/http.ts` (кеш, ретраї, ліміт паралельності, офлайн-режим,
позначка походження даних), `lib/stats.ts` (чиста статистика), `lib/analyze.ts` (метрики й
оцінка довіри), `lib/chart.ts`, `lib/report.ts`, `lib/format.ts` (вивід для агента).

### Що допомагає агенту на дешевій моделі

- **Одна команда = один крок робочого процесу**; вивід компактний (таблиця + KEY FACTS + причини
  довіри + прапорці), а не сирий JSON.
- **KEY FACTS** — заздалегідь сформульовані правильні речення: модель перекладає їх, а не
  інтерпретує числа сама (перший прогін Haiku показав, що саме тут вона помиляється).
- **Вбудована перевірка висновків**: інтервали, «distinguishable: yes/no» для порівнянь, «без
  сплесків», сира vs відносна динаміка, CLAIM CHECK для PDF, попередження про цілісність даних.
- **Повторні й пов'язані запити дешеві**: кеш на диску, повна історія одним запитом, тому «а за
  5 років?» чи «додай німецьку» — це повторний `analyze` з іншими прапорцями без зайвих запитів.
- Помилки пояснюють, що робити (і чого не робити — наприклад, не «дописувати» кеш).

### Припущення й обмеження (відображаються у звітах)

Перегляди — це увага, не готовність платити; стаття — проксі теми; мовний розділ ≠ країна;
загальне падіння трафіку Wikipedia (відповіді ШІ/пошуку) компенсується лише частково через
нормалізацію; боти, що маскуються під людей, можуть давати сплески; для тем без статті в
певній мові інтерес «невидимий».

## Як перевірялося

1. **Unit-тести** (`tests/core.test.ts`): місяці, коди сайтів, зростання/ДІ (детермінованість),
   sign-test, Sen's slope на експоненті, сплески, класифікація довіри (стабільне зростання → high,
   зростання через один сплеск → знижено, мізерний обсяг → low, нова стаття → прапорець), парсер нотаток.
2. **Синтетичний API** (`tests/fake-fetch.ts`) для end-to-end прогону без мережі та візуальної
   перевірки графіків і PDF (рендер у PNG і ручний огляд).
3. **Реальні дані**: середовище розробки не мало прямого доступу до wikimedia.org, тому відповіді
   API були отримані через браузер і імпортовані в кеш (`WV_RECORD_MISSES` + `tools/import-responses.ts`);
   значення перехресно звірені між двома запитами з різними діапазонами.
4. **Прогони на Claude Haiku 4.5** за сценаріями з `evals/scenarios.md`; журнал помилок і
   виправлень — `evals/results.md`. Найважливіше, що вони виявили: неправильне тлумачення
   відносних змін (→ KEY FACTS), фабрикацію даних в офлайн-режимі (→ жорсткі правила, позначка
   походження кешу, DATA INTEGRITY WARNING), нестачу кешу для інших періодів (→ повна історія).
5. Код писався з AI-асистентом; кожну зміну перевіряли `tsc --strict`, тестами, реальними
   прогонами й оглядом згенерованих графіків/PDF.

## Як розвивати далі (ітеративно)

**Етап 1 — надійність відповіді (найближче)**
- Прогнати всі сценарії `evals/` онлайн, додати сценарій 3 (англійська у top20) у регресійний набір;
  автоматизувати eval-раннер через OpenRouter (дешеві/безкоштовні моделі) з перевіркою чекліста.
- Перевірка «без причинних тверджень»: попереджати, якщо в notes.md є «через/because…» без джерела.
- Автоматичний текст методики не лише en/uk (шаблони для pl/cs/de/…).

**Етап 2 — кращі проксі теми**
- Кошики статей: автоматично пропонувати суміжні статті (Wikidata-властивості, категорії,
  «what links here») і показувати, яка частка інтересу припадає на яку статтю.
- Пошук локальних статей, коли в мові немає відповідника (через langlinks суміжних тем).
- Розбивка desktop vs mobile і ручний контроль «automated»-трафіку.

**Етап 3 — більші дослідження й обсяги**
- Сканування «всі мови × багато тем»: пакетний режим із пріоритизацією, чергою запитів
  (≤100 req/s за політикою Wikimedia), відновленням після збою й прогресом.
- Сховище: перехід з JSON-кешу на SQLite/Parquet (один файл на проект), інкрементальне
  дозавантаження лише нових місяців.
- Для сотень тисяч статей — дампи Wikimedia (pageview complete dumps) замість API.
- Щоденна гранулярність і детекція подій (news-driven) з анотаціями.

**Етап 4 — сильніша статистика й контекст**
- Сезонна декомпозиція (STL) і прогноз з інтервалами; врахування автокореляції в тестах.
- Поправка на множинні порівняння при скануванні багатьох мов/тем.
- Зовнішні ваги ринків: кількість носіїв, ВВП на особу, проникнення смартфонів — щоб
  «інтерес» перетворювати на «ринок», з чітким поділом «дані Wikipedia» vs «зовнішні припущення».
- Порівняння з іншими сигналами (Google Trends, пошукові обсяги) для тріангуляції.

**Етап 5 — продукт**
- Збережені «дослідження» (параметри + висновки), щоб наступні запити будувалися на попередніх.
- Щомісячний моніторинг обраних тем із сповіщенням про зміну тренду.
